# Лаборатория пяти решений — только для кода

## Назначение и приоритеты

После исследования и адаптации клиента, до сборки полного пути, создай пять работающих вариантов ключевого экрана или короткого взаимодействия. Это этап brief-to-prototype, не отдельный запуск design-lab. Варианты всегда собираются сначала в коде; Figma предлагается только для выбранного финального решения после проверки полного кодового прототипа. Основные ограничения цепочки — один клиент, один успешный путь, заданное оформление, обязательная оболочка без презентации — сохраняются. Правила раздела «Визуальный язык и тексты» в SKILL.md обязательны для каждого варианта и имеют приоритет над общими примерами из design-lab-quality.md.

Лаборатория обязательна по умолчанию. Пропускай её только по прямому поручению пользователя или при продолжении уже утверждённого решения. Запиши причину; экономия времени сама по себе не основание сокращать пять вариантов до одного. Не создавай пять полных продуктов: каждый вариант реализует выбранный фрагмент с одинаковыми границами и видимым результатом действия.

## 1. Подготовка без повторного интервью

Прочитай brief.md, исследование, адаптацию клиента и существующую память решений. Перед проектированием проверь, что кандидаты представлены и клиент выбран по разделу 3 SKILL.md. До выбора не создавай варианты. Во всех A–E используй контекст одного выбранного человека: его обстоятельства, потребности, привычки и ограничения должны влиять на решения, а не только на имя и суммы. Связь фактов профиля с решениями сохраняй в материалах задачи. Уточняй только отсутствующие сведения, которые меняют решение. Определи ключевой момент через критерий успеха: где пользователь принимает решение, вводит важные данные или завершает основное действие. Сохрани выбранный фрагмент и его границы.

Определи фреймворк, маршрутизацию, пакетный менеджер и систему стилей по проекту. Осмотри существующие кнопки, формы, карточки, типографику и токены. Используй их только в пределах оформления design-scenario; не заменяй SB Sans Display или заданную палитру стилями старого проекта. Для нового проекта следуй code-prototype.md.

До реализации прочитай актуальные core-ios-style.md, code-prototype.md, скилл оболочки и его starter в объёме design shell, затем `design-lab-quality.md`. Общие данные вынеси в один fixture из адаптации клиента; каждому варианту дай независимое состояние. Изменение суммы в A не меняет B. Переключение вариантов сохраняет состояние каждого. Если добавлена кнопка «В начало сценария», она возвращает только активный вариант на первый шаг с исходными данными; остальные варианты сохраняются. Повторное нажатие активной буквы ничего не сбрасывает.

## 2. Пять самостоятельных гипотез

До кода запиши матрицу A–E: гипотеза, структурное отличие, польза для задачи, основание из исследования (ссылка или явно «гипотеза»), компромисс и наблюдаемый критерий сравнения.

| Вариант | Основная ось | Требование |
|---|---|---|
| A | Иерархия информации | Другой порядок и группировка содержания, ясное главное действие |
| B | Компоновка | Другая организация пространства: список, карточки, сводка с деталями или иной подход, подходящий мобильному экрану |
| C | Плотность и раскрытие | Другая порция информации за шаг, компактность либо постепенное раскрытие; обязательные сведения остаются доступны |
| D | Модель взаимодействия | Другой способ выполнить ту же задачу: inline, панель, sheet, последовательность шагов; рабочий цикл действия |
| E | Выразительность и акценты | Иная композиция, визуальный ритм и подача результата в той же палитре и типографике; не простая смена цвета или радиуса |

Ось задаёт главный эксперимент, а не запрещает связанные изменения. У каждой пары вариантов должно быть объяснимое отличие в структуре или поведении. Если отличие сводится к украшению, переработай вариант до показа. Не назначай заведомо слабые варианты ради количества. Во всех пяти сохрани задачу, клиента, значения, смысл обязательных текстов и результат. Перегруппировка и сокращение текста допустимы без потери смысла. Новые клиенты, случайные суммы и дополнительные продуктовые ветки не являются разнообразием решений.

## 3. Рабочая лаборатория

Создай отдельный работающий маршрут `/design-lab` либо режим `?design_lab=true` под существующий стек. В Next.js App Router не используй буквальную папку `__design_lab`: папки с начальным `_` исключаются из маршрутизации. Не перезаписывай занятый маршрут — выбери свободный и сохрани фактический URL.

Храни код вариантов в обычном компилируемом каталоге проекта, например `src/design-lab/`. Метаданные, матрицу и решения по обратной связи из чата — в каталоге задачи `design-exploration/`. В manifest.json перечисли только созданные файлы и внесённые изменения интеграции для последующей безопасной очистки.

Показывай один активный вариант в полном размере. Над ним или рядом, вне продуктового экрана, размести один горизонтальный ряд компактных кнопок A–E: только буквы, без названий и описаний. Как в референсе: равные скруглённые кнопки, активная чёрная с белой буквой, остальные белые с тёмной буквой. Ориентир — 44–48 px по стороне, промежуток 6–8 px, радиус 14–16 px. Не растягивай кнопки на ширину панели. Для созданного синтеза добавь F в тот же ряд. На узком экране сохраняй доступность ряда без уменьшения области нажатия ниже 44 px.

Разрешена только одна дополнительная кнопка «В начало сценария», если нужен повторный проход. Это полный список операторских контролов лаборатории. Не добавляй «Сравнить», «Сбросить», «Выбрать A», комментарии, выбор элемента, экспорт, настройки iOS/Android, темы, размеров, скругления, меню или скрытые панели с этими функциями. Не подключай модуль комментариев, его обработчики, хранилище или зависимости. Продуктовые действия внутри сценария сохраняются.

Кнопки букв переключают просмотр, а не утверждают направление. Итоговый выбор и правки пользователь сообщает в чате. Используй нативные button с доступным именем «Вариант A» и aria-pressed для активного варианта, видимым фокусом и работой через клавиатуру. Изолируй стили контролов от продукта. Не создавай сетку сравнения, отдельный режим просмотра или дополнительные кнопки подтверждения.

Каждый вариант использует сцену design shell, но её параметры заданы в коде, без панели настроек. Это исключение имеет приоритет над скиллом оболочки и starter. Чистая ссылка варианта на мобильном показывает только продукт во весь экран; буквенный ряд остаётся на отдельной лабораторной странице. Не выводи бриф, описания, гипотезы, обоснования и матрицу в интерфейс; сохраняй их в материалах задачи.

Все основные действия фрагмента работают: ввод, переход/раскрытие, подтверждение и видимый результат. Mock-поведение обозначай в передаче; не выполняй реальные операции. Реализуй применимые состояния элементов (focus, active, disabled, validation, loading), но не добавляй незаказанные ошибки и ветки в продуктовый путь ради чеклиста.

## 4. Проверка и показ

До показа лаборатории проведи редакторский прогон каждого A–E по разделу «Редакторская проверка до показа» в SKILL.md и правилам design-scenario. Проверь все экраны и переходы выбранного фрагмента, включая последовательное раскрытие деталей без информационных дублей и глубину до трёх шагов от исходного экрана. Одноэкранный вариант не нужно расширять ради этой проверки. Запиши результаты отдельно по вариантам, исправь найденное и повторно проверь затронутые участки. Синтез F и последующие доработки проходят ту же проверку перед повторным показом. Проверка сборки и скриншотов не заменяет редакторский прогон.

Запусти проект доступным способом в управляемом фоновом процессе, дождись готовности и открой реальный маршрут. Не используй запрет upstream на запуск dev server: в этой цепочке нужен проверенный результат. Проверь сборку/проверки проекта, затем в браузере каждый из A–E, действие до результата, переключение A → B → A с сохранением независимых состояний, возврат в начало (если кнопка добавлена), узкую и широкую ширину и отсутствие утечки стилей. Сними фактические скриншоты вариантов и ключевых состояний, проверь переполнение, переносы, шрифт, контраст и фокус. Если браузерная проверка недоступна, назови ограничение; успешная сборка не заменяет визуальную проверку.

Проверь состав операторской области: только буквы вариантов и не более одной кнопки «В начало сценария», без модулей комментариев и дополнительных настроек. Проверь также соблюдение правил визуального языка: смысловые визуальные элементы, отсутствие технических подписей в продукте и описаний вариантов в лаборатории.

Выдай реальную ссылку, ссылку на сохранённую матрицу отличий и инструкцию: «Переключай варианты буквами. Напиши в чате выбранную букву и нужные правки». Попроси выбрать A–E либо части нескольких вариантов. Останови только зависимую сборку полного сценария до ответа; молчание не означает выбор. Если пользователь явно поручил выбрать самостоятельно, обоснуй выбор по критерию брифа и продолжай.

## 5. Синтез и полный сценарий

Прочитай выбор и правки пользователя из чата. Исправь победителя или собери F из названных частей; сохрани 1–2 ближайших оригинала для сравнения. Запиши, что взято и что изменено. Поддерживай итерации, пока направление не выбрано; не генерируй новые пять вариантов при каждой правке. Для редизайна покажи исходный и предлагаемый вариант на одинаковых данных.

После выбора перенеси решение в полный успешный путь в коде по design-scenario. Продолжай работу в рамках уже порученной цепочки, не останавливайся на DESIGN_PLAN.md. Проведи редакторский прогон и проверку пути в обязательной оболочке. Фидбэк дизайнера — основание выбора, не доказательство удобства реальным пользователям; синтетический клиент не заменяет исследование.

Перед очисткой перенеси выигравший код и зависимости в постоянные файлы, запиши design-decisions.md и убедись, что финальный маршрут не импортирует удаляемую лабораторию. По умолчанию убирай временные маршруты лаборатории только после переноса и проверки. Сохраняй матрицу, обратную связь из чата, причины выбора и скриншоты в материалах задачи. Если пользователь попросил оставить лабораторию — сохрани её отдельно от чистого входа. При паузе сохрани всё для продолжения; при явной отмене убирай только созданные лабораторные файлы по manifest, не удаляй бриф, исследование, клиентскую адаптацию и пользовательский код. Не откатывай целиком файл с чужими изменениями.

После проверки полного кодового прототипа выполни этап «Предложение собрать финальный вариант в Figma» из SKILL.md.

## 6. Состояние и передача

В brief.md сохрани:

```yaml
design_exploration:
  status: pending # comparing | refining | approved | implemented | skipped
  target: null
  reason: null # границы выбора или причина пропуска
  variants: [A, B, C, D, E]
  iteration: 1
  selected: null
  decision_reason: null
  lab_url: null
  clean_preview_url: null
  artifacts_path: design-exploration/
  verification: []
```

Матрица, фактические URL, manifest, fixtures, обратную связь из чата и design-decisions.md должны быть доступны по ссылкам из брифа. В decision record сохраняй выбранное решение, причины, отклонённые подходы, оставшиеся гипотезы и границы проверки. В scenario-handoff.md добавь выбранный вариант/гибрид, ссылку на решения и чистый старт полного прототипа. Статус implemented ставь только после проверки полного пути, а не после генерации лаборатории.
