# Лаборатория пяти решений — только для кода

## Назначение и приоритеты

После исследования и адаптации клиента, до сборки полного пути, создай пять работающих вариантов ключевого экрана или короткого взаимодействия. Это этап brief-to-prototype, не отдельный запуск design-lab. Варианты всегда собираются сначала в коде; Figma предлагается только для выбранного финального решения после проверки полного кодового прототипа. Основные ограничения цепочки — один клиент, один успешный путь, заданное оформление, обязательная оболочка без презентации — сохраняются. Правила раздела «Визуальный язык и тексты» в SKILL.md обязательны для каждого варианта и имеют приоритет над общими примерами из design-lab-quality.md.

Лаборатория обязательна по умолчанию. Пропускай её только по прямому поручению пользователя или при продолжении уже утверждённого решения. Запиши причину; экономия времени сама по себе не основание сокращать пять вариантов до одного. Не создавай пять полных продуктов: каждый вариант реализует выбранный фрагмент с одинаковыми границами и видимым результатом действия.

## 1. Подготовка без повторного интервью

Прочитай brief.md, исследование, адаптацию клиента и существующую память решений. Перед проектированием проверь, что кандидаты представлены и клиент выбран по разделу 3 SKILL.md. До выбора не создавай варианты. Во всех A–E используй контекст одного выбранного человека: его обстоятельства, потребности, привычки и ограничения должны влиять на решения, а не только на имя и суммы. Связь фактов профиля с решениями сохраняй в материалах задачи. Уточняй только отсутствующие сведения, которые меняют решение. Определи ключевой момент через критерий успеха: где пользователь принимает решение, вводит важные данные или завершает основное действие. Сохрани выбранный фрагмент и его границы.

Определи фреймворк, маршрутизацию, пакетный менеджер и систему стилей по проекту. Осмотри существующие кнопки, формы, карточки, типографику и токены. Используй их только в пределах оформления design-scenario; не заменяй SB Sans Display или заданную палитру стилями старого проекта. Для нового проекта следуй code-prototype.md, не навязывай React исключительно ради шаблона комментариев.

До реализации прочитай актуальные core-ios-style.md, code-prototype.md, скилл оболочки и его starter в объёме design shell, затем `design-lab-quality.md`. Общие данные вынеси в один fixture из адаптации клиента; каждому варианту дай независимое состояние. Изменение суммы в A не меняет B. Настройки оболочки не сбрасывают состояние текущего варианта. Добавь явный сброс к исходным данным для честного повторного сравнения.

## 2. Пять самостоятельных гипотез

До кода запиши матрицу A–E: гипотеза, структурное отличие, польза для задачи, основание из исследования (ссылка или явно «гипотеза»), компромисс и наблюдаемый критерий сравнения.

| Вариант | Основная ось | Требование |
|---|---|---|
| A | Иерархия информации | Другой порядок и группировка содержания, ясное главное действие |
| B | Компоновка | Другая организация пространства: список, карточки, сводка с деталями или иной подход, подходящий мобильному экрану |
| C | Плотность и раскрытие | Другая порция информации за шаг, компактность либо постепенное раскрытие; обязательные сведения остаются доступны |
| D | Модель взаимодействия | Другой способ выполнить ту же задачу: inline, панель, sheet, последовательность шагов; рабочий цикл действия |
| E | Выразительность и акценты | Иная композиция, визуальный ритм и подача результата в той же палитре и типографике; не простая смена цвета или радиуса |

Ось задаёт главный эксперимент, а не запрещает связанные изменения. У каждой пары вариантов должно быть объяснимое отличие в структуре или поведении. Если отличие сводится к украшению, переработай вариант до показа. Не назначай заведомо слабые варианты ради количества. Во всех пяти сохрани задачу, клиента, значения, смысл обязательных текстов и результат. Перегруппировка и сокращение текста допустимы без потери смысла. Новые клиенты, случайные суммы и дополнительные продуктовые ветки не являются разнообразием решений.

## 3. Рабочая лаборатория

Создай отдельный работающий маршрут `/design-lab` либо режим `?design_lab=true` под существующий стек. В Next.js App Router не используй буквальную папку `__design_lab`: папки с начальным `_` исключаются из маршрутизации. Не перезаписывай занятый маршрут — выбери свободный и сохрани фактический URL.

Храни код вариантов в обычном компилируемом каталоге проекта, например `src/design-lab/`. Метаданные, матрицу и комментарии — в каталоге задачи `design-exploration/`. В manifest.json перечисли только созданные файлы и внесённые изменения интеграции для последующей безопасной очистки.

Лаборатория содержит пять вариантов с обозначениями A–E, визуальное сравнение самих прототипов и просмотр одного варианта в полном размере. Не выводи бриф, описания вариантов, гипотезы, обоснования, компромиссы и текстовую матрицу сравнения в интерфейс лаборатории; сохраняй их в материалах задачи. На десктопе используй 2–3 колонки, только если экраны помещаются без уменьшения текста; иначе переключатель/полноразмерный просмотр. Не сжимай мобильный интерфейс ради сетки.

Каждый вариант представлен в обязательной design shell. Селектор A–E, комментарии и сброс принадлежат операторской области снаружи продукта. Это рабочие инструменты сравнения, не презентационная оболочка. Чистая ссылка варианта на мобильном показывает только продукт во весь экран. Для мобильного сравнения оставь отдельную лабораторную страницу; не внедряй её контролы в продукт.

Все основные действия фрагмента работают: ввод, переход/раскрытие, подтверждение и видимый результат. Mock-поведение обозначай в передаче; не выполняй реальные операции. Реализуй применимые состояния элементов (focus, active, disabled, validation, loading), но не добавляй незаказанные ошибки и ветки в продуктовый путь ради чеклиста.

## 4. Комментарии к элементам

Для React скопируй `../assets/design-lab/FeedbackOverlay.tsx` из этого скилла рядом с лабораторным компонентом и импортируй относительным путём. Это автономный upstream-шаблон с React/ReactDOM, встроенными типами, стилями, выбором элементов, сохранением и экспортом; соседние utils из оригинального плагина ему не нужны. Проверь совместимость с проектом, не обещай готовность по факту копирования.

Оборачивай каждый вариант в `data-variant="A"` ... `"E"`; синтезированный — `"F"`. Добавляй устойчивые `data-testid` ключевым элементам. Render `<FeedbackOverlay targetName="TaskName" />` один раз на странице лаборатории. Не включай его в чистый продуктовый маршрут.

Адаптация при интеграции:
- Локализуй видимые подписи под язык задачи, изолируй стили от продукта.
- Используй ключ хранения с идентификатором задачи и итерации, чтобы комментарии разных лабораторий не смешивались. Обработай недоступный localStorage без падения UI.
- Режим просмотра сохраняет нормальные клики продукта; режим комментариев перехватывает только выбор комментируемого элемента. Выход возвращает управление; обработчики удаляются при размонтировании.
- Проверь закрытие по Escape, фокус в редакторе/диалоге и возврат фокуса. Предусмотри клавиатурный способ оставить комментарий к варианту без точного клика.
- Если clipboard недоступен, покажи выделяемый текст для ручного копирования. Не заявляй автоматическую передачу комментариев агенту: пользователь вставляет экспорт в чат.
- Для другого стека реализуй эквивалент: вариант + элемент + текст + общее направление + экспорт. Не подключай React к чужому стеку только ради overlay.

Перед показом проверь полный цикл: добавить комментарий в A, добавить в D, изменить/удалить, перезагрузить, экспортировать; ID вариантов и тексты должны сохраниться. Ручной фидбэк в чате также допустим, но отсутствие работающего overlay не скрывай.

## 5. Проверка и показ

Запусти проект доступным способом в управляемом фоновом процессе, дождись готовности и открой реальный маршрут. Не используй запрет upstream на запуск dev server: в этой цепочке нужен проверенный результат. Проверь сборку/проверки проекта, затем в браузере каждый из A–E, действие до результата, сброс, переключение, узкую и широкую ширину, настройки оболочки и отсутствие утечки стилей. Сними фактические скриншоты сравнения и ключевых состояний, проверь переполнение, переносы, шрифт, контраст и фокус. Если браузерная проверка недоступна, назови ограничение; успешная сборка не заменяет визуальную проверку.

Проверь также соблюдение правил визуального языка: смысловые визуальные элементы, отсутствие технических подписей в продукте и описаний вариантов в лаборатории.

Выдай реальную ссылку, ссылку на сохранённую матрицу отличий и инструкцию: «Добавь комментарии к элементам, укажи общее направление, скопируй и вставь сюда — или опиши выбор в чате». Попроси выбрать A–E либо части нескольких вариантов. Останови только зависимую сборку полного сценария до ответа; молчание не означает выбор. Если пользователь явно поручил выбрать самостоятельно, обоснуй выбор по критерию брифа и продолжай.

## 6. Синтез и полный сценарий

Сначала прочитай общее направление, затем комментарии по элементам. Исправь победителя или собери F из названных частей; сохрани 1–2 ближайших оригинала для сравнения. Запиши, что взято и что изменено. Поддерживай итерации, пока направление не выбрано; не генерируй новые пять вариантов при каждой правке. Для редизайна покажи исходный и предлагаемый вариант на одинаковых данных.

После выбора перенеси решение в полный успешный путь в коде по design-scenario. Продолжай работу в рамках уже порученной цепочки, не останавливайся на DESIGN_PLAN.md. Проведи редакторский прогон и проверку пути в обязательной оболочке. Фидбэк дизайнера — основание выбора, не доказательство удобства реальным пользователям; синтетический клиент не заменяет исследование.

Перед очисткой перенеси выигравший код и зависимости в постоянные файлы, запиши design-decisions.md и убедись, что финальный маршрут не импортирует удаляемую лабораторию. По умолчанию убирай временные маршруты и overlay только после переноса и проверки. Сохраняй матрицу, экспорт комментариев, причины выбора и скриншоты в материалах задачи. Если пользователь попросил оставить лабораторию — сохрани её отдельно от чистого входа. При паузе сохрани всё для продолжения; при явной отмене убирай только созданные лабораторные файлы по manifest, не удаляй бриф, исследование, клиентскую адаптацию и пользовательский код. Не откатывай целиком файл с чужими изменениями.

После проверки полного кодового прототипа выполни этап «Предложение собрать финальный вариант в Figma» из SKILL.md.

## 7. Состояние и передача

В brief.md сохрани:

```yaml
design_exploration:
  status: pending # comparing | refining | approved | implemented | skipped
  target: null
  reason: null # границы выбора или причина пропуска
  variants: [A, B, C, D, E]
  iteration: 1
  selected: null
  decision_reason: null
  lab_url: null
  clean_preview_url: null
  artifacts_path: design-exploration/
  verification: []
```

Матрица, фактические URL, manifest, fixtures, экспорт комментариев и design-decisions.md должны быть доступны по ссылкам из брифа. В decision record сохраняй выбранное решение, причины, отклонённые подходы, оставшиеся гипотезы и границы проверки. В scenario-handoff.md добавь выбранный вариант/гибрид, ссылку на решения и чистый старт полного прототипа. Статус implemented ставь только после проверки полного пути, а не после генерации лаборатории.
